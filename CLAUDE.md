# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A reverse-engineering project for the University of Hawaii's Student Information System (Ellucian **Banner SSB9** course search). It has two halves that share the same understanding of the SIS API but no code:

1. **`discovery/`** — one-off, exploratory Python + Playwright tools that *discovered* the API by driving the real UI in a headless browser and intercepting traffic. These produced the docs and the OpenAPI spec. They talk to the live UH server. (Distinct from `web/scripts/`, which is the Node ingest CLI.)
2. **`web/`** — An Astro SSR app that *reimplements* the discovered API as direct HTTP "API mimicry" (no browser), exposing a course-search UI and JSON endpoints backed by a server-side session pool and cache.

The canonical reference for how the SIS API works is **`docs/walkthrough.md`** (request lifecycle, token propagation, all 31 endpoints, full search parameter list) and **`openapi.yaml`** (formal spec). Read the walkthrough before touching `web/src/lib/sis/` — the session handshake there is a direct translation of it.

## The SIS session handshake (core domain knowledge)

Banner SSB9 is a stateful JavaEE/Tomcat app behind an F5 BIG-IP load balancer with CSRF protection. Any client must replay this exact sequence (see `web/src/lib/sis/client.ts:establishSession`):

1. `GET /ssb/term/termSelection?mode=search` → sets `JSESSIONID` + `BIGipServer...` cookies, and embeds **Token_A** in a `<meta name="synchronizerToken">` tag.
2. `POST /ssb/term/search?mode=search` (form-encoded `term`, `uniqueSessionId`) with Token_A → locks the term into the session (302 redirect).
3. `GET /ssb/classSearch/classSearch` → returns a **refreshed Token_B** in the same meta tag.
4. All subsequent search / contact-card / details calls use **Token_B** in the `x-synchronizer-token` header plus the cookie jar.

Key invariants: the synchronizer token is passed as the `x-synchronizer-token` header (not a cookie); Token_A and Token_B are *different* and the switch happens at step 3; the BIGip cookie name varies (it embeds the server pool) so code matches by `startsWith("BIGipServer")`; server sessions expire after ~30 minutes. Most details-modal endpoints return raw HTML fragments, not JSON.

**The search form is stateful server-side.** Banner stores the previous search's criteria against the session, so a pooled/reused session "remembers" the last search. `searchCourses` therefore issues `POST /ssb/classSearch/resetDataForm` (Token_B, empty body, returns `"true"`) *before* every `searchResults` call — without it, changed filters like `txt_courseNumber` are silently ignored and the table shows the prior results. This is the single most subtle correctness trap in the client; don't remove the reset.

## web/ architecture

Astro `output: "server"` with the Node standalone adapter; React islands for interactivity; Tailwind v4 via the Vite plugin; shadcn/ui components under `src/components/ui/`.

**Where the data lives (since 2026-11-24).** The account is on the Workers **Free** plan, whose 500 MB D1 cap the 2.2 GB search DB exceeds, so both databases now live as SQLite files on a home Ubuntu server (Docker Compose, `deploy/home/`). The Worker still serves everything; its only DB seam, `src/lib/db/binding.ts`, returns a fetch-based `D1Like` (`src/lib/db/gatewayClient.ts`) whenever `DB_GATEWAY_URL` is set. It talks to the **SQL gateway** (`web/gateway/server.ts`: `POST /v1/query {db, statements, batch}`, bearer secret, `batch:true` = one transaction) through host-level cloudflared + Cloudflare Access (service token). With `DB_GATEWAY_URL` unset it falls back to the native D1 bindings. Every gateway call is a Worker subrequest (~50/invocation on Free), so keep per-request query counts low (e2e asserts a page-cache fill stays ≤ 30, and that an uncached backfilled-term search is exactly 2 calls: the term sync-meta read, then `searchSections`' COUNT + page as one `db.batch` — `runSearch` hands that meta down to `ensureSearchPage` rather than re-reading it). Each call is a ~20 ms tunnel round-trip in production versus <1 ms of SQLite time, so call count is effectively the read path's latency. The daily refresh runs as `yarn ingest daily` in the compose `cron` service (supercronic, 22:00 HST); `RefreshWorkflow` is still deployed but **unscheduled**. All SQLite opens go through `openSqliteFile` (WAL + `busy_timeout`, FKs off) so reads continue during ingestion. Runbook: `deploy/home/README.md`; design: `docs/superpowers/specs/2026-11-24-home-backend-design.md`. Where this file says "D1" below, read "the D1-compatible store" — the SQL is unchanged.

The app is split into a **read path** (user-facing, served entirely from a persistent Cloudflare D1 store) and **write paths** (Banner-facing ingestion/refresh jobs that populate D1). The live Banner API is never on the request hot path. Design + rationale: `docs/plans/d1-persistence.md`; the deferred Cloudflare Workers hosting migration: `docs/plans/workers-migration.md`.

**Read path** (each layer only calls the one below):
- **`src/pages/api/{search,terms,filters,course,section,instructor}.ts`** — thin Astro API routes; parse/validate/clamp params, map errors to HTTP status. `filters` serves server-driven dropdown menus (incl. `kind=subject`, derived from the term's sections); `course` serves catalog facts + text for one course (keyed by `term+campus+subject+courseNumber`); `section` serves per-CRN detail (restrictions/fees/cross-list/…); `instructor` serves contact-card facts by `bannerId`. `search` filters by `campus`, `college`, and `department`; **`subject` is optional — omitting it searches all subjects in the term.** `search` also has a **CRN mode**: a `crn` param identifies exactly one section (a CRN is unique only *within* a term — never globally — and Banner's search form has no CRN field), so it ignores every other filter and returns that single section. `search` is also the one read route that may trigger a live Banner call: for a not-yet-backfilled ("dynamic") term it serves searches from a demand-driven, sort-aware **page cache** — fetching only the viewed page(s) live from Banner and recording coverage (see page cache below); a CRN miss on a dynamic term likewise falls back to a single live fetch (`crnLazy`).
- **`src/lib/search.ts`** — application layer; calls the DB query layer (no cache, no Banner, no session).
- **`src/lib/db/queries.ts`** — `getTerms`, `searchSections` (reproduces Banner's filter/sort/paginate in SQL; sort whitelisted; LEFT JOINs `course` for the campus/college/department filters; `subject` is an optional filter — empty = all subjects), `getFilterOptions`, `getCatalogFacet`, `getSubjectFacet` (the Subject menu — the union of subjects with sections and the enumerated `subject` table, so un-backfilled terms still list subjects once enumerated), `getCourseCatalog`. Sections are reconstructed byte-faithfully from a stored `raw_json` blob (`src/lib/db/mappers.ts`). **College/Department menus are derived from the `course` table (`getCatalogFacet`), not `filter_option` — UH disables `get_college`/`get_department`/`get_scheduleType`/`get_partOfTerm` in their Banner config (confirmed live; `filter_option` only carries campus/subject/attribute/level/instructionalMethod).** Catalog facts are per `(term, campus, subject, course)` — the same course at another campus is a different catalog entry.
- **`src/lib/db/client.ts`** — a narrow `D1Like` interface with two backends: `remoteD1` (D1 REST API, for a deployed Node host) and `localSqliteD1` (Node `node:sqlite` over the wrangler local D1 file, for dev/tests). Selected by `D1_MODE`. On Workers the native `env.DB` binding satisfies `D1Like` directly. The Worker entry is `web/src/worker.ts` (re-exports the `@astrojs/cloudflare` handler as `fetch` plus `RefreshWorkflow`); `wrangler.jsonc` has a `workflows` binding, currently **without** a `schedules` cron (the daily refresh moved to `yarn ingest daily` on the home server; re-add `"schedules": ["0 8 * * *"]` to move it back, which needs Workers Paid). `RefreshWorkflow` runs **bounded steps per term** — enumerate subjects → one sync step per ~40-subject session-batch → finalize → prune-dropped → plan-details → details in `DETAIL_STEP_SIZE`-CRN chunk steps (B1 ∪ stalest restrictions, deduped + per-run capped via `planTermDetailCrns`, fetched whole-row by `syncDetails` — it does not use the per-fragment/crseavail daily path) — so no step approaches the 10-min step timeout even for the ~9k-section term.

**Write path** (Banner-facing; only these touch the live SIS):
- **`src/lib/sis/client.ts`** — the SIS HTTP client and handshake: `establishSession`, `getTerms`, `getSubjects`, `resetSearchForm`, `searchCourses`, `getEnrollmentInfo` (live per-CRN seat counts; no current caller — the standalone seat-refresh path was removed, but the primitive is kept for a future per-class refresh feature), plus the course-details fetchers `getFilterOptions` (the `get_*` menus), `getCatalogDetails`, and `getClassDetails` (the per-CRN modal that echoes a section's subject + catalog course number — used by the CRN-lookup fallback). HTML-fragment parsers live in `src/lib/sis/parse/`.
- **`src/lib/crseavail/`** — validated client (`client.ts`) for UH's public Class Availability JSON API (crseavail; no session handshake, `X-Recaptcha-Token: undefined` + a desktop-Chrome UA, 20 s timeout, ≤ 2 retries) plus the mapping to our rows (`map.ts`). Ingestion uses it for **course facts** (per `(term, campus, subject)` unit: credits/hours, college/department codes, description, grading modes) and **term-wide cross-lists**. Every unit is checked (rows ≥ 90% of our sections, ≥ 95% of its CRNs known, non-empty when we hold data); a rejected unit falls back to Banner for exactly its courses, and the first unit is a preflight — its failure or 5 consecutive rejections trip a per-run breaker to Banner-only (a `RunBreaker` shared by every term of the invocation, which also keeps the term-wide cross-list write off crseavail). crseavail never deletes or writes NULL (except the guarded term-wide cross-list write). On only when `CRSEAVAIL=1`; units are fetched serially, `CRSEAVAIL_DELAY_MS` apart. Fallbacks (rejected unit + reason, breaker trip, cross-list fallback) go to the run's `log` callback (ungated); the `[CA]` tag (silenced by `LOG_SOURCE=0`) is only per-call chatter.
- **`src/lib/ingest/*`** — `sync.ts` (full catalog sync: enumerate subjects, paginate; delete-and-replace replaced by a per-section delta — `syncTerm` reads stored rows and writes only changed/new/dropped sections: seat-only changes UPDATE the row without rewriting child rows; unchanged sections are skipped — to conserve D1 writes on the daily refresh; `syncTerm` is factored into `enumerateSyncSubjects` + `syncSubjectBatch` so the Workflow can drive Tier A as bounded per-session-batch steps), `terms.ts` (term-list refresh + `is_view_only` recompute — populates **every** term, no section backfill), `details.ts` (Banner-only course-details phase used by the Workflow and the `sync-details` route: filter-option menus, course-level catalog/text from one representative CRN per `(campus,course)`, and per-CRN `section_detail`, written by the per-fragment fetchers (`fragments.ts`, `bannerCourseFacts`); also `materializeCatalogFacets` — see `docs/plans/course-details.md`), `refresh.ts` (the daily refresh orchestrator for non-view-only terms, run by `yarn ingest daily` and the `refresh-run` admin route: Tier A full sync, then `refreshTermDetails` works **per fragment**, each with its own `*_synced_at` cursor — course facts for the whole term from **crseavail** (`syncCourseFacts`, mode `all`) with automatic per-unit Banner fallback capped at `REFRESH_ROLLING_FACTS_COURSES` plus the B1 courses; B1 = new ∪ structural CRNs from the diff get restrictions + extras (dropped CRNs pruned); **rolling** restrictions / extras refresh the `REFRESH_ROLLING_RESTRICTION_CRNS` (500) / `REFRESH_ROLLING_EXTRAS_CRNS` (300) stalest CRNs by that fragment's stamp, never-fetched first (`getStaleSectionCrns`); cross-list is term-wide from crseavail, else Banner for B1 ∪ rolling extras (`syncCrossList`); prereqs/coreqs (Banner) for B1 courses never fetched ∪ courses whose crseavail description changed ∪ the `REFRESH_ROLLING_PREREQ_COURSES` (150) stalest (`getStalePrereqCourses`). The instructor contact-card pass is gone. Each term's summary reports `restrictionsRolled`/`extrasRolled`/`prereqsRolled`, `crseavail` (`crseavail`|`degraded`|`off`), `crossList` and `detailsStatus`, and a `sync_run` kind `details` row carries the crseavail health in `notes`. The unscheduled `RefreshWorkflow` still uses the older whole-row path: `planTermDetailCrns` (B1 ∪ stalest restrictions, capped at the restrictions cap) fetched by `syncDetails` in bounded chunk steps); also `diff.ts` for the section-core change classifier — whose `structuralFingerprint` deliberately **excludes** Banner's ephemeral per-query faculty `bannerId` (keying on it churned every instructor-bearing section "structural" every sync → details-step timeout), keying faculty on `emailAddress`/`displayName` instead), `backfill.ts` + `capture.ts` (the **gap-driven, time-boxed, resumable capture** driver, `yarn ingest backfill [--term] [--dryRun] [--maxMinutes]`: completeness is judged from the data — `getTermGaps`/`listTermsWithGaps` find CRNs missing a fragment stamp and courses missing a facts/prereq stamp — and `captureTerm` fills only those gaps (crseavail facts with uncapped Banner fallback, cross-list, restrictions, extras, prereqs), active terms first then view-only newest-first, term after term until the deadline (`--maxMinutes`, default 180, never past 21:45 HST when started before it); an interrupted run resumes where it stopped, and a term whose last capture finished with the same gaps left is skipped for up to 7 days. Recorded as `sync_run` kind `capture` with gap counts in `notes`. Run by `deploy/home/run-capture.sh` (crontab 09:00/13:00/17:00 HST), which shares the daily job's lock file)), `sectionLazy.ts`, `courseTextLazy.ts`, `dynamicSync.ts`, `pageCache.ts`, and `crnLazy.ts` (the cache-on-miss paths invoked from read routes — see below). HTML-fragment parsers live in `src/lib/sis/parse/`.

**Cache-on-miss (the only live-Banner calls on a user request).** Several lazy paths fill gaps on first view and serve from D1 forever after, invoked from the API routes (never the query layer, so it stays Banner-free):
- `sectionLazy.ensureSectionDetail` — per-CRN section detail (`/api/section`); fetches only the fragment groups still missing (restrictions; extras = fees+linked+syllabus; cross-list — judged by `restrictions_synced_at`/`extras_synced_at`/`crosslist_synced_at`; on-view cross-list matters for dynamic terms, which ingest never captures), writes them with the per-fragment writers, and returns the merged row (a stored partial row is served when nothing can be fetched).
- `courseTextLazy.ensureCourseText` — per-course description/prereqs/coreqs (`/api/course`); the eager catalog pass ran `text=0`, so the trigger is now `prereq_synced_at IS NULL`: prereqs+coreqs are always fetched then, the description only if `description IS NULL`, via `updateCoursePrereqs`/`updateCourseDescription`.
- `pageCache.ensureSearchPage` — the demand-driven **page cache** (`/api/search`). For a dynamic term, fetches **only the offset window(s) the user is viewing** live from Banner (`searchCourses` omits `txt_subject` for an all-subjects page — Banner returns the whole sorted, paginated term), stores the bodies in `course_section` (`upsert.upsertSections`, keyed `term,crn` — no delete window), and records each filled window in `search_chunk`, keyed by **sort order + the live-applied filters** (`subject`/`courseNumber`/`openOnly`; college/department are catalog-derived and unavailable for dynamic terms). The read side reassembles a page from cached windows (`queries.getSearchPageFromChunks`). Windows are a fixed internal size (`CHUNK_SIZE`); view-only terms are immutable so a window never expires, other terms revalidate after `PAGE_TTL_MS`. Coverage fills incrementally as users page through. Replaces the old per-`(term,subject)` lazy sync.
- `dynamicSync.ensureTermSubjects` — the term's subject **menu** (`/api/filters?kind=subject`); one `getSubjects` call so a not-yet-backfilled term's Subject dropdown isn't empty (`term.subjects_synced_at` marks it ran, so a term with zero subjects isn't re-hit).
- `crnLazy.ensureSectionByCrn` — one section by `(term, crn)` for the search route's CRN mode (`/api/search?crn=`). A CRN search has no subject/course-number to page on, and Banner has no CRN search field, so on a D1 miss it calls `getClassDetails(term, crn)` to learn the catalog course number (and confirm the CRN exists), runs a course-number-scoped `searchResults` to pick the matching row, and stores it. Backfilled terms already hold every section, so a miss there is a genuine "no such section" — no live call.

The dynamic paths only fire for a term that was never fully backfilled (`term.last_synced_at IS NULL`); backfilled terms serve searches entirely from D1 via the SQL path, so they never trigger. All are gated by env flags (`SECTION_LAZY_FETCH`, `COURSE_TEXT_LAZY`, `DYNAMIC_SYNC`) and dedupe concurrent first-hits. The on-view section/course fetches share a per-isolate rate limit (`lazyLimit.tryTakeLazySlot`, `LAZY_FETCH_PER_MINUTE`, default 30/min; only live fetches take a slot). e2e marks the read-path fixture terms backfilled so their searches stay on the SQL path, and exercises the page cache against a dedicated dynamic term (`COURSE_TEXT_LAZY=0` keeps the course panel off the mock). Dev logs tag every request path: **`[DB]`** (served from D1) vs **`[SIS]`** (a live Banner call) via `src/lib/log.ts` (`LOG_SOURCE=0` to silence). **Known gap:** College/Department menus (catalog-derived) stay empty for an un-backfilled term until its catalog is synced — only subjects + the viewed section pages are filled dynamically.
- **`src/lib/db/upsert.ts`** — all D1 writes + `sync_run` bookkeeping; the granular delta writers `insertSectionsAndChildren`, `deleteSectionsAndChildren`, and `updateSectionRows` are called by `syncTerm` based on the classification from `classifyForWrite` (`src/lib/ingest/diff.ts`); `replaceSubjectSections` was removed. **Per-row `course_section.synced_at` is "last modified"** — delta writes skip unchanged rows so their `synced_at` no longer bumps every sweep; `term.last_synced_at` is "last verified" (bumped once per successful sync). The coverage/freshness grid's per-window `MIN/MAX(synced_at)` therefore reflects modification recency, not last-verify time.

**Analytics rollups (a second D1 database).** A separate D1 database `uh-analytics-db` (binding `ANALYTICS_DB`, migrations in `web/migrations-analytics/`) holds pre-aggregated analytics rollups: `course_term_stats` (per term+course+campus), `term_facet_stats` (per term+facet, facet ∈ `all`/`campus`/`college`/`schedule_type`), `term_meeting_stats` (per term+campus+day-of-week+start-hour, for the meeting heatmap; `migrations-analytics/0002`), plus `analytics_meta`. Rollups are computed by `src/lib/ingest/rollups.ts` (`computeTermRollups`/`computeAllRollups`): it **reads** the search DB and **writes** the analytics DB — there is **no cross-DB JOIN** (rollups are self-contained), and it preserves `capped_sections` (count of sections with `maximum_enrollment > 0`) so a fill-rate has an honest denominator. Driven by `yarn ingest rollups` (one-time historical population; admin route `POST /api/admin/rollups` is the e2e/ops seam) and a per-term `rollups ${code}` step in `RefreshWorkflow` (daily, mutable terms only). The read path mirrors the search read path but binds **only `ANALYTICS_DB`**: thin routes `src/pages/api/analytics/{courses,enrollment-trend,university-trend,delivery-mode,meeting-heatmap}.ts` → app layer `src/lib/analytics.ts` → SQL `src/lib/db/analyticsQueries.ts`. These routes are edge-cached via `analyticsCacheProfile()` (`src/lib/edgeCache.ts`) keyed on a date-bucketed (UTC `YYYY-MM-DD`) version, so a cache hit computes its key with zero D1 reads (rollups recompute at most once daily). The UI is the `/analytics` page (`src/pages/analytics.astro`) rendering an `AnalyticsApp` React island (`src/components/analytics/`) with these charts — course enrollment over time, university enrollment trend (campus⇄college toggle), delivery-mode shift (100%-stacked schedule types), and a meeting-time heatmap (day-of-week × start-hour, CSS grid — not Recharts) — drawn inside shadcn-styled containers; a `Search | Analytics` header nav lives in `src/layouts/Layout.astro`.

**Prerequisite graph (read-only derived data).** The `course_prereq` (AST, one row per course) and `prereq_edge` (flat edges, one row per course-pair-alternative) tables store **one** prerequisite graph — for the single newest **primary** active term (`getPrimaryActiveTerm`: newest non-view-only term excluding Extension/Apprenticeship/Accelerated sub-terms; e.g. Fall 2026, not Fall 2026 Extension). Prereqs are catalog-level and ~identical across a cycle's terms and the read path only serves one graph, so building every active term would be ~4× the storage + daily writes for no benefit (and would make the newest-by-code term an Extension term). Node identity = `(term, campus, course_id)` where `course_id` is subject + display-number with no space (e.g., `ICS311`). Edges have `group_index` (which requirement block; most courses have 0) and `alt_index` (which OR-alternative within the block; rows differing in `alt_index` are substitutable; rows sharing `(group_index, alt_index)` are AND-ed). Built by `src/lib/ingest/prereqGraph.ts` (`buildPrereqGraph`/`buildAllPrereqGraphs`), which parses prerequisite text via the shared `src/lib/prereq/parse.ts` parser (also used by the UI), resolves course references to canonical node ids via `src/lib/prereq/resolve.ts` (normalizing entity-encoded subject descriptions — section `subject_description` is `&amp;`-encoded, parsed prereq text is decoded), and performs a delete-and-replace write per term+campus. `course_prereq` stores only the parsed `ast_json` (+ non-course notes); the raw text is **not** copied (it lives in `course.prerequisites`). Driven by `yarn ingest prereqs` (builds the primary term; pass `--term` to override; admin route `POST /api/admin/prereqs` is the e2e/ops seam) and a single `prereqs` step in `RefreshWorkflow` (daily, after the per-term `rollups` loop). The read path is `GET /api/prereqs?course=ICS311&campus=...&direction=[prereqs|unlocks|both]&depth=3` → `src/lib/prereqs.ts` → `src/lib/db/prereqQueries.ts` (cycle-guarded BFS, depth-clamped; the served term defaults to the one with rows and is returned as `term` in the response). Results are edge-cached (date-bucketed like analytics). The `/prereqs` page (`src/pages/prereqs.astro`) is a React island explorer (`src/components/prereq/`) using React Flow + dagre for layout (URL-synced inputs via nuqs, draggable nodes, theme-aware), with MCP tool support (`get_prereq_graph`).
- **`src/pages/api/admin/{sync,sync-details,refresh-terms,refresh-run,backfill,prereqs}.ts`** — secret-guarded (`x-admin-secret`) triggers; `sync-details` runs after a full sync (it enumerates the live course set from D1); `refresh-terms` populates the `term` table with every Banner term (no section backfill — the rest fill in on demand via the page cache); `refresh-run` triggers the daily refresh (Tier A + per-fragment details) via `refreshMutableTerms`; `backfill` runs `backfillNextTerm` (the gap-driven capture; `?dryRun=1` lists gap terms without calling Banner — the e2e seam, since the CLI isn't reachable over HTTP); `prereqs` rebuilds the prerequisite graph via `buildAllPrereqGraphs`. All admin routes are Node-only (`INGEST_ON_WORKER` unset → 501 in prod). POSTs must send `Content-Type: application/json` to clear Astro's CSRF origin check.

D1 schema lives in `web/migrations/` (`wrangler d1 migrations apply uh-course-search-db [--local|--remote]`). `0001` is the core search model; `0002` adds the additive course-details tables (`course`, `filter_option`, plus `section_detail`/`instructor` reserved for later slices) — these are *new native tables*; `0006` adds `search_chunk` (the demand-driven page cache's per-window coverage for dynamic terms); `0008` added `term.last_details_synced_at` and `0009` drops it again — the weekly-full-pass staleness marker it gated was superseded by rolling refresh, and detail freshness is now read from the per-fragment stamps added in `0017` (`restrictions_synced_at`/`extras_synced_at`/`crosslist_synced_at`, `prereq_synced_at`), which the rolling cursors order by; `0011` drops the dead `enrollment_snapshot` table (semester-to-semester history is read from `course_section`, so no separate snapshot table is needed); `0012` adds `section_attribute` (per-section Banner attribute codes — Focus/Gen-Ed/IDAP — mirrors `section_faculty`), written during sync and backfilled from `raw_json` by `yarn ingest backfill-attributes`; the search read path filters on it (ANY/ALL) and sources the attribute menu from it (not `filter_option`); `course_section` + `raw_json` stays Banner-faithful (hybrid, per `docs/plans/course-details.md`); `0013` adds `course_prereq` (course-level AST) + `prereq_edge` (flat edges), one primary-active-term graph per campus, built by `yarn ingest prereqs`; `0014` drops `course_prereq.raw_text` (it duplicated `course.prerequisites`); `0015` adds `idx_cs_term_campus (term, campus_description, subject, open_section)` so the search COUNT under a campus filter is a covering scan (the default Manoa landing search's count was fetching every row of the term) — `subject` is in the key because, with no `sqlite_stat1`, the planner otherwise picks it over `idx_cs_subj_sort` for subject+campus counts and those regress; `e2e/search-indexes.spec.ts` pins these plans; `0016` adds `term.usual_start_date/usual_end_date` — the term's **usual meeting date range** (the most common `(begin_date, end_date)` pair, only if it covers ≥ 60% of the term's meetings, else NULL; `src/lib/db/usualDates.ts`), refreshed by `markTermSynced` on every `ok` sync and filled once for all terms by `yarn ingest usual-dates` — and repairs NULL `section_meeting.begin_date` rows from `raw_json` (the meeting mapper read Banner's non-existent `beginDate` before `d748a20`, and the delta sync never rewrote those unchanged rows). The range rides on every `/api/search` response as `usualDateRange` (read in the per-request term-meta query, and part of the edge-cache version); the results table's **Schedule** column (`src/components/ScheduleCell.tsx`: one spanning header over four real table columns — Days | Time | Room | Dates — with one fixed-height no-wrap line per meeting, untimed meetings last) shows a meeting's dates only when they differ from it. `0017` adds the per-fragment freshness stamps — `section_detail.restrictions_synced_at`/`extras_synced_at`/`crosslist_synced_at`, `course.facts_synced_at`/`facts_source` (`crseavail`|`banner`)/`prereq_synced_at` (backfilled from `synced_at`), and `sync_run.notes` (JSON run summary) — which drive the per-fragment writers, the rolling refresh cursors and the capture gap queries. The analytics rollup DB has its own migrations dir, `web/migrations-analytics/`. `SIS_BASE_URL`, `D1_MODE`, `CLOUDFLARE_ACCOUNT_ID`, `D1_DATABASE_ID`, `ANALYTICS_DATABASE_ID`, `CLOUDFLARE_API_TOKEN`, `ADMIN_SECRET`, `CRSEAVAIL` (`1` = use crseavail; anything else = Banner only), `CRSEAVAIL_BASE_URL` (default `https://www.sis.hawaii.edu:9350/crseavail/api`), `CRSEAVAIL_DELAY_MS` (pause between crseavail units, integer ≥ 0, default 250, read at call time), and the daily refresh's per-run caps `REFRESH_ROLLING_RESTRICTION_CRNS` (500; falls back to the retired `REFRESH_ROLLING_DETAIL_CRNS` when only that is set), `REFRESH_ROLLING_EXTRAS_CRNS` (300), `REFRESH_ROLLING_PREREQ_COURSES` (150) and `REFRESH_ROLLING_FACTS_COURSES` (150, the Banner-fallback course-facts budget) come from env (see `web/.env.example`).

> Note: the previous in-memory `cachified`/`unstorage` cache and the in-memory session pool (`src/lib/cache/`, `src/lib/sis/session.ts`) have been removed — D1 is the source of truth and the handshake now runs once per ingestion job, not per request.

### web/ (Yarn 4, run from `web/`)
```bash
yarn dev        # astro dev server
yarn build      # production build (also the real typecheck — astro check's binary doesn't resolve under PnP)
yarn preview    # serve the build
yarn test       # playwright e2e (all browsers)
yarn test --project=chromium                 # single browser
yarn test -g "course number filter"          # single test by title
yarn ingest refresh-run [--term 202710] [--delayMs 200]  # Tier A+B orchestrated refresh
yarn ingest backfill [--term 202700] [--dryRun] [--maxMinutes 180]  # gap-driven capture, time-boxed + resumable
yarn ingest prereqs [--term 202710]                      # rebuild prerequisite graphs
yarn ingest usual-dates [--term 202710]                  # recompute term usual meeting date ranges (Schedule column)
yarn ingest daily [--term 202710]                        # the cron entry point: refresh + rollups + prereqs
yarn ingest crseavail-parity --term 202710               # read-only gate: crseavail vs stored Banner facts (calls crseavail even if CRSEAVAIL unset); exit 1 unless ≤ 5% of mapped units failed to fetch or failed ingestion's unit checks (`coverage`), the cross-list fetch worked, at least one course fact was compared, and every compared field >= 99%
yarn gateway                                             # home SQL gateway (GATEWAY_SECRET, SEARCH_/ANALYTICS_D1_LOCAL_FILE)
yarn db:migrate-sqlite --db search|analytics --file <f>  # apply pending migrations to a self-hosted SQLite file
yarn db:backup [--dir /data/backups] [--keepDays 14]     # VACUUM INTO dated backups + prune
E2E_NATIVE_D1=1 yarn test                                # e2e on the native D1 bindings instead of the gateway
```
Note: the **root** also has a `package.json` with `workspaces: ["web"]` and Yarn PnP (`.pnp.cjs`); run `yarn` from the root (or `web/`) to install. The `yarn astro check` typecheck cannot find its binary under Yarn PnP, so rely on `yarn build` for type errors.

**Env loading.** Server config (`D1_MODE`, `SIS_BASE_URL`, the Cloudflare D1 creds, `ADMIN_SECRET`) is read from `process.env`. Vite only surfaces `.env` via `import.meta.env`, so `astro.config.mjs` calls `process.loadEnvFile("./.env")` at the top — this is what makes **`yarn dev` pick up `web/.env`** (without it `D1_MODE` is unset → defaults to `local` → dev serves the e2e fixture, not the remote store). `loadEnvFile` never overrides already-set vars, so an explicit shell export wins and e2e's `D1_MODE=local` is unaffected. The built standalone server (`yarn preview`) does **not** load `astro.config.mjs`, so preview/ingestion runs still need env exported first (`set -a; . ./.env; set +a`).

E2E tests live in `web/e2e/` and run the **full Astro SSR build** (`build` + `preview`); Playwright's `webServer` launches both the app and the mock SIS server (`web/e2e/mock-sis-server.mjs`) — never the live UH host. Two flavors:
- **Read-path** (`search.spec.ts`, all browsers) — served from a **seeded local D1**. `e2e/global-setup.ts` applies the local migration and inserts a fixture catalog; the app reads it via `D1_MODE=local`. No SIS involved.
- **Ingestion** (`ingest.spec.ts`, chromium only — it mutates shared D1) — drives the Banner-facing sync/seat-refresh through the admin routes against the mock SIS, writing to the same local D1. The mock reproduces Banner's stateful-form quirk, and the sync reuses one session across two subjects, so the test is the genuine regression guard for the `resetDataForm` reset.

Tests use the production build (not `dev`) to keep the Astro dev toolbar out of the DOM.

## discovery/ orientation

These are one-off exploratory tools — the live scraping/ingestion now runs in Node under `web/`. Two kinds, documented fully in `docs/discovery.md`:
- **Live (hit the real UH server via Playwright):** `verify_all_endpoints.py` (sequential 200-OK check of all 31 endpoints → `verification_report.json`), `scrape_banner.py` (captures traffic → `intercepted_calls.json`), `confirm_search_params.py`, and the cookie/token diagnostics (`find_tokens.py`, `get_session_cookies.py`).
- **Offline (analyze the dumped `intercepted_calls.json`, no network):** the `inspect_*.py` family + `validate_openapi.py`.

When the SIS API behavior is in question, prefer re-running the offline `inspect_*` scripts against the existing dumps before hitting the live server.
